# Career Quest — архитектура MVP v1

Это согласованный проект команды, а не требование организатора использовать именно эти технологии. Цель: неизвестный профиль жюри + история → объяснимая рекомендация → отметка выполнения → изменённые навыки и следующий шаг → HR-срез.

## Стек и роли

- React SPA + TypeScript + Vite; Tailwind CSS для интерфейса, без Next.js и отдельного Node-сервера в итоговой сборке. Небольшие графики допустимы, новая дизайн-система не нужна.
- Python 3.12, FastAPI, Pydantic, Uvicorn. JSON и CSV читаются стандартной библиотекой; Pandas не обязателен.
- SQLite через sqlite3, один авторитетный источник состояния во время работы. Исходные файлы служат для первоначального импорта и тестов, не вторым изменяемым хранилищем.
- Существующий engine.py + ограниченный LLM-выбор кандидатов через OpenAI Responses API / Structured Outputs. Модель задаётся OPENAI_MODEL; доступ и задержку проверяют реальным разрешённым запросом.
- Demo-аккаунты employee/hr/admin, пароли хешируются; короткоживущий подписанный JWT. Нет регистрации, refresh-token системы, банковского SSO.
- Один runtime-контейнер: multi-stage сборка React → Python/FastAPI раздаёт static SPA и /api. SQLite хранится в volume. Финальный запуск: `docker compose up --build` после подготовки окружения по README.

AI-разработчик владеет доменной математикой: effective skills, gaps, readiness, scoring, LLM, проверкой объяснений. Backend владеет хранением, транзакциями, доступом и адаптером данных. Frontend ничего самостоятельно не пересчитывает.

## Поток чтения и рекомендации

1. FastAPI проверяет подписанный токен, действительность аккаунта, роль и доступ к конкретному employee_id.
2. Repository читает согласованный snapshot из SQLite и строит `engine.Data`. Это временный объект вычисления, не отдельное хранилище.
3. Движок получает эффективные навыки, цель, дефициты, baseline top-3 и до пяти валидных кандидатов.
4. При доступном API LLM выбирает 1–3 существующих кандидата, учитывает несколько факторов, ссылается на подготовленные сервером факты. Запрос работает только на одном языке.
5. Валидатор проверяет схему, принадлежность event_id, уникальность, fact_id, связь фактов с выбранным событием, не менее трёх доступных категорий обоснования и защиту лидера.
6. Ответ содержит рекомендации, проверяемые факторы, причины, source=llm|fallback, reason fallback, флаг override, state_revision и измеренную задержку.

Когда кандидатов нет, вернуть пустой список и конкретную причину: цель достигнута, нет доступной активности, не выполнены prerequisites, каталог не закрывает разрыв. Не выдумывать три курса ради количества.

## Ограниченный LLM, не свободный агент

Сохранить baseline движка. LLM участвует в содержательном выборе среди близких допустимых кандидатов; не является автором фактов, формулы и чисел. Никаких инструментальных агентов, чата, RAG, embeddings или обучения модели.

Начальная эвристика защиты лидера: лидер имеет положительный ненулевой score и либо второй score неположителен, либо отношение первого ко второму >= 1.35; альтернативный сигнал — единственный доступный кандидат, закрывающий конкретный незакрытый критичный навык. Уникальность оценивать по всему допустимому пулу, не только top-5. Сравнивать неокруглённые score. Если кандидатов 0/1 — отдельные ветки без деления на ноль.

Защищённый лидер остаётся ПЕРВЫМ, не просто где-то в списке. При нарушении вернуть его на первое место, убрать дубли, добавить его серверное объяснение, записать leader_override=true. Полностью невалидный ответ → весь deterministic fallback. Не делать второй LLM-запрос для исправления. Коэффициент 1.35 — проверяемая настройка MVP, не доказанная гарантия правильности и не требование ТЗ.

LLM возвращает event_id, fact_ids и короткое объяснение. Полные reason_factors берутся из серверного реестра фактов. Показываемые проверенные причины можно рендерить шаблонами по этим факторам. Проверка структуры не доказывает истинность свободного текста: сомнительный текст заменять шаблоном; не заявлять «галлюцинации исключены».

История не доказывает мотивацию сотрудника: no_show не означает лень или отказ от развития. Нет истории — отметить отсутствие данных, а не выдавать prior за личный completion rate. Нельзя использовать пол, этничность, предполагаемую психологию и другие чувствительные признаки.

Один язык на запрос: явно выбранный lang, иначе preferred_language. Кеширование разделить: порядок выбора на snapshot/config и локализованный текст на этот порядок+язык. Переключение языка не должно незаметно менять сами рекомендации. Ключ включает employee_id, state_revision, язык, версию алгоритма/промпта и модель. После Complete/import старая версия не используется.

Выделить LLM около 6 секунд с общим application deadline около 8 секунд; отключить автоматические повторы SDK. Это инженерный бюджет, не обещание задержки. Измерять весь маршрут и проверять требование рекомендации до 10 секунд. Таймаут, отказ, некорректная схема, лимит API, отсутствие ключа → deterministic fallback с честной пометкой. Для полноценного AI-демо нужен работающий реальный API; fallback не заменяет обязательный AI-слой.

## Источники данных и прогресс

Прочитать `data/README.ru.md` и реальные JSON, не пример из чата вместо схемы. В исходном архиве:
- условное «сегодня» модели — 2026-10-01; брать `meta.as_of_date`, а не системную дату;
- роль, грейд, цель, prerequisites и максимумы берутся из набора;
- отсутствующий skill равен 0;
- исходные skills относятся к last_review_date; завершения после этой оценки надо учитывать ровно один раз;
- mandatory не рекомендуется;
- после completed событие не повторяется, кроме EV_036 — регулярного клуба.

SQLite хранит базовую оценку, историю и текущие отметки выполнения. НЕ делать одновременно update baseline skills += gain и добавление учитываемой истории: это удвоит прирост. Доменный код один: применять существующий effective_skills (расширив его минимально при необходимости), а не копии формулы в API и UI.

Завершение — транзакция: проверка прав/события/участия → запись или завершение конкретного участия → увеличение state_revision → commit → пересчёт snapshot. Повтор той же операции не даёт второй gain. Для EV_036 различать занятия по occurrence_key, иначе либо повторное нажатие даст лишний gain, либо клуб нельзя будет повторять. Даты/происхождение новых отметок хранить так, чтобы завершение после оценки в тот же модельный день не потерялось; явно протестировать этот случай. Обновление оценки при повторном импорте не должно повторно применять уже включённые в неё завершения.

Текущий уровень никогда не уменьшается из-за низкого max_level: after=max(before,min(5,before+gain,max_level)). Это правило для одного воздействия. Порядок/учёт истории сохраняет движок.

Readiness — степень покрытия требований по навыкам, НЕ вероятность повышения. Сохраняем формулу существующего engine.readiness: 100*sum(min(current,required))/sum(required), округление для UI; критичные навыки показываются отдельно. Не менять grade автоматически и не обещать повышение после достижения 100%.

## Импорт

Стартовый набор импортируется при пустой SQLite. Повторный запуск не перетирает прогресс. Жюри передаёт employees JSON и history CSV через один multipart-запрос /api/admin/upload. Валидация обоих файлов до записи; один transaction; ошибки файла/строки/поля без traceback. Проверить роли/грейды/цели, skill_id, шкалу 0–5, даты и статусы, employee/event/record_id. Связи проверяются с учётом всех новых сотрудников в том же запросе.

Повтор идентичного импорта не дублирует history. Конфликт record_id с другим содержимым — 409 без частичной записи. Профили с существующими employee_id обновляются явно как новая версия данных; правила взаимодействия с текущими demo-completions документировать и протестировать. После импорта вернуть ids и количество строк; новый профиль сразу доступен admin для проверки.

## Доступ, приватность, demo-login

Employee: свой профиль, свои рекомендации, своя история, своё выполнение. Другой employee_id → 403 (не выдавать данные даже при прямом HTTP-запросе). HR: служебный срез, список сотрудников/индивидуальная проверка согласно роли. Admin: дополнительно импорт и демонстрационное выполнение/просмотр проверочных профилей. /auth/me возвращает права с сервера; выбор роли в браузере не создаёт полномочий.

Никаких публичных рейтингов, передачи всей базы сотрудников в SPA, API-ключа во frontend. JWT проверять подпись/exp и пользователя. Несколько demo-аккаунтов с хешированными паролями достаточно; отсутствие регистрации не означает отсутствие аутентификации. Не обещать production-уровень защиты.

OpenAI получает только необходимые обезличенные факторы выбранного сотрудника и каталог кандидатов, а не всю SQLite/фамилии/контакты/архив истории. Согласовать допустимость внешней обработки в рамках ограничений организатора. store=false не равен гарантии нулевого хранения провайдером. Не класть токены и полные запросы в логи.

## Приёмка

Обязательная проверка: чистый запуск; вход employee/hr/admin; доступ к чужому профилю запрещён; импорт неизвестного профиля+истории; три и более локальных профиля-ловушки; объяснение минимум по трём факторам; Complete и повтор Complete; новый прогресс и рекомендации; обновление HR; отсутствие кандидатов; реальный LLM; отказ/таймаут LLM; RU/KK; рестарт с сохранением SQLite; одна команда запуска.

HR без рекомендаций определяется по доступным кандидатам, не по отсутствию ответа LLM/кеша. HR-обзор не вызывает модель для каждого сотрудника. Рост readiness/смена курса после Complete зависит от данных: нельзя жёстко подставлять другой event_id ради демо.

Optional за пределами MVP: магазин наград, монеты, отток, календарь/мессенджеры, голос, чат, прогноз гарантированного повышения. Простой RU/KK интерфейс; EN fallback. README, lockfiles, .env.example и описание ограничений делаются по ходу работы.
